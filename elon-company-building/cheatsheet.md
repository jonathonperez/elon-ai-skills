# Cheatsheet — Decide Like Elon

## Decision rules
- When given a requirement → demand the *name* of the person who made it; no name → delete it. Departments can't own requirements.
- When a part/process survives step 1 → try to delete it anyway; if you never re-add ~10% of deletions, you're under-deleting.
- When tempted to optimize or automate → first ask "should this exist at all?" Never speed up what should be deleted.
- When a component is quoted → compute idiot index (finished ÷ materials). High ratio → in-house it or adapt a commodity part from a cheaper industry.
- When told "impossible" → ask "does it break the laws of physics?" No → ask "what would it take?"
- When money can buy time → spend it (the $90k plane). When it buys convenience → don't (the $2k part).
- When something urgent breaks → go there physically, today, and meet on it every 24h until fixed; then stop the meetings.
- When you get a bad unit off the line → root-cause to the *design*, not the operator.
- When hiring → attitude over resume; check the character of their friends; prefer people already obsessed with the problem. Would you interview Nikola Tesla?
- When a manager can't do their team's actual work → they install roofs / write code tomorrow (≥20% ongoing).
- When choosing between decisiveness and accuracy → decide now; expect 20% wrong and correct fast. "If I don't make decisions, we die."
- When you win → put the winnings back on the table. When you fail publicly → own it by name ("my mistake") and state the long-haul commitment.
- When someone stands up to you with evidence → promote them, don't punish them (Shotwell rule).
- When wronged by partners → keep the bridge; you may need it in six years.
- When picking what to work on → does it fail without you? Is it useful (help per person × people helped)? Mission first; backfill the economics.
- When pitching → build the demo instead of the deck.
- When a meeting stops needing you → leave. "It is rude to make someone stay."

## Thresholds & defaults he commits to
| Rule | Number |
|---|---|
| Deletions you should re-add later | ≥10% (else under-deleting) |
| Technical managers doing hands-on work | ≥20% of time |
| Command decisions/day on the floor, wrong rate accepted | ~100/day, ~20% wrong |
| Losses before emotion fades and risk-taking improves | ~50 |
| Cadence on existential problems | every 24 hours |
| Failures that prove real work | "four ways you screwed up before you got it right" |

## Tells & smells
- Requirement defended by a department name → it's unowned; probably deletable.
- Nobody can say who specified it → delete it now (plastic-caps case: nothing broke).
- Two teams each say the other required it → Dilbert loop; test empirically, then delete.
- Chain-of-command routing of information → org rot; product flaws incoming.
- Executive can't quote their worst idiot-index parts → they don't know their area.
- Growing internal acronym glossary → communication decaying at scale.
- Veterans "phoning in rich" → hunger gone; inject fresh blood.
- Timeline feels long → it's wrong. Cut it, then cut again.
- "Psychological safety" as core value → complacency risk; urgency dying.
- You feel like you're winning → assume you're losing; recheck the truth channel.

## The mantras (repeat to an annoying degree)
- A maniacal sense of urgency is our operating principle.
- The best part is no part. Delete, delete, delete.
- Physics is law; everything else is a recommendation.
- The only true currency is time.
- All bad news loudly and often; good news quietly and once.
- If conventional thinking makes the mission impossible, unconventional thinking is necessary.
- We must make stuff. If we don't make stuff, there is no stuff.
